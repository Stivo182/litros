# Устойчивый фасад менеджера сущностей

## Контекст

В приложении операции с SQLite выполняются непосредственно через `МенеджерСущностей` библиотеки `entity`, а сырой SQL — через полученный из него коннектор. Часть операций очереди уже вручную обёрнута в `ИсполнительОперацийБД`, но остальные репозитории обходят единый pipeline. Особенно опасен `ХранилищеЗависимыхРепозиториев`: оно вручную открывает транзакцию, выполняет несколько CRUD-операций и вызывает другой репозиторий внутри этой транзакции.

Простое добавление retry вокруг каждого существующего вызова не решает задачу. Повтор отдельного шага внутри транзакции нарушает атомарность, а повторное занятие singleton-pipeline с лимитом параллелизма `1` из уже выполняемой операции приводит к ожиданию собственного слота.

## Цели

- Дать коду `litros` единый интерфейс для отказоустойчивых CRUD-операций и сырого SQL.
- Повторять транзакционную операцию целиком: `BEGIN → работа → COMMIT`.
- Перед каждой повторной попыткой после успешного `BEGIN` гарантированно выполнить `ROLLBACK`.
- Исключить вложенный запуск `ИсполнительОперацийБД` внутри транзакции.
- Скрыть сырой `МенеджерСущностей`, коннектор и Active Record от мигрированных потребителей.
- Сохранить поведение и типы результатов используемых методов `entity`.

## Не входит в задачу

- Полная drop-in-совместимость со всем API `МенеджерСущностей` библиотеки `entity`.
- Публичная обёртка для `СоздатьЭлемент`, `ПолучитьХранилищеСущностей`, `ПолучитьКоннектор`, управления моделью или жизненным циклом соединения.
- Изменение алгоритма retry и настроек pipeline. Единственное расширение классификатора — приоритетный служебный маркер невозобновимой ошибки транзакции, описанный ниже.
- Обеспечение exactly-once для произвольных внешних побочных эффектов. Транзакционный callback должен содержать только операции с той же SQLite-базой.
- Поддержка вложенных транзакций и savepoint в первой версии.
- Изменение публичного API библиотеки `entity`.

## Рассмотренные подходы

### 1. Явный executor в каждом потребителе

Каждый репозиторий самостоятельно создаёт `Действие` и передаёт его в `ИсполнительОперацийБД`.

Плюс — минимум новых абстракций. Минусы — дублирование, лёгкий обход pipeline и отсутствие единого безопасного шаблона для транзакций. Текущая очередь уже показывает, что обёртки приходится расставлять вручную, а при миграции возможен двойной executor.

### 2. Полный прозрачный proxy над `entity`

Proxy повторяет весь интерфейс `МенеджерСущностей`, включая выдачу коннектора, хранилищ и Active Record.

Плюс — формальная совместимость. Минусы — большой и нестабильный контракт, зависимость от внутренних особенностей `entity` и сохранение способов обойти отказоустойчивость. Прозрачно и безопасно переопределить семантику Active Record и произвольного коннектора невозможно.

### 3. Прикладной фасад `УстойчивыйМенеджерСущностей`

Фасад предоставляет только операции, реально используемые `litros`, и направляет их через один `ИсполнительОперацийБД`. Для транзакций он выдаёт ограниченную `ЕдиницуРаботыБД`, которая обращается к исходному менеджеру напрямую и поэтому не запускает вложенный pipeline.

Это выбранный подход. Он ограничивает поверхность API, делает границу отказоустойчивости явной и позволяет мигрировать потребителей постепенно. Цена — целенаправленное изменение зависимостей репозиториев и запрет на часть API `entity` в мигрированном коде.

## Компоненты

### `УстойчивыйМенеджерСущностей`

Новый прикладной класс в `src/internal/Классы`. Он зависит от:

- внутреннего исходного `МенеджерСущностей`;
- singleton `ИсполнительОперацийБД`.

Каждый нетранзакционный метод создаёт служебное действие, выполняющее ровно один прямой вызов исходного менеджера, и один раз передаёт это действие в `ИсполнительОперацийБД.ВыполнитьОперацию`. Фасад не выполняет дополнительной классификации ошибок: решение о повторе остаётся у существующего executor и `КлассификаторОшибокSQLite`.

### `ЕдиницаРаботыБД`

Новый внутренний класс хранит ссылку на тот же исходный `МенеджерСущностей`, на котором фасад открыл транзакцию. Он предоставляет прямые `Получить`, `ПолучитьОдно`, `Сохранить`, `Удалить` и `ВыполнитьЗапрос`, но не содержит executor и не предоставляет методы управления транзакцией, получения коннектора, хранилища или Active Record.

Единица работы действительна только во время одного вызова транзакционного callback. Фасад деактивирует её после `COMMIT` или попытки `ROLLBACK`. Любой последующий вызов сохранённой единицы работы завершается программной ошибкой до обращения к БД. Это не позволяет вынести прямой доступ за границы транзакции.

## Прикладной API

Фасад сохраняет сигнатуры и результаты соответствующих операций `entity`:

```text
Получить(ТипСущности, ОпцииПоиска = Неопределено) -> Массив
ПолучитьОдно(ТипСущности, ОпцииПоиска = Неопределено) -> Произвольный | Неопределено
Сохранить(Сущность)
Удалить(Сущность)
ВыполнитьЗапрос(ТекстЗапроса) -> ТаблицаЗначений
ВыполнитьВТранзакции(Операция, Параметры = Неопределено) -> Произвольный
```

`ВыполнитьЗапрос` внутри фасада и единицы работы вызывает `ПолучитьКоннектор().ВыполнитьЗапрос()` исходного менеджера. Сам коннектор наружу не возвращается.

`ВыполнитьВТранзакции` принимает публичное `Действие` и параметры по тем же правилам, что и pipeline `resilience`:

- `Неопределено` не добавляет пользовательских аргументов;
- произвольное значение становится одним аргументом;
- элементы `Массив` или `ФиксированныйМассив` становятся отдельными аргументами.

При вызове callback фасад всегда добавляет действующую `ЕдиницуРаботыБД` первым аргументом, после неё — пользовательские аргументы. Например, для параметров `[ИмяПакета, Репозитории]` callback имеет сигнатуру `Операция(ЕдиницаРаботы, ИмяПакета, Репозитории)`.

Методы единицы работы имеют те же первые пять сигнатур, но выполняются напрямую, без retry. `ВыполнитьВТранзакции` у неё отсутствует.

## Алгоритм транзакции

`ВыполнитьВТранзакции` занимает `ИсполнительОперацийБД` один раз на всю логическую операцию. Каждая попытка executor выполняет следующую последовательность:

1. Вызвать `НачатьТранзакцию()` исходного менеджера.
2. Создать активную `ЕдиницуРаботыБД` для этого менеджера.
3. Вызвать пользовательское действие с единицей работы и параметрами.
4. Вызвать `ЗафиксироватьТранзакцию()`.
5. Деактивировать единицу работы и вернуть результат действия.

Если после успешного `BEGIN` действие или `COMMIT` завершились ошибкой, фасад сохраняет исходную информацию об ошибке, выполняет `ROLLBACK`, деактивирует единицу работы и только после успешного rollback повторно выбрасывает исходную ошибку. Поэтому классификатор видит исходную SQLite-ошибку, а executor при необходимости повторяет всю последовательность с шага 1.

Если `BEGIN` завершился ошибкой, единица работы ещё не создана и прикладные изменения не выполнялись. Фасад пробрасывает эту ошибку в executor без `ROLLBACK`; временная ошибка может быть повторена как новая попытка.

## Ошибки и гарантии

### Ошибка прикладной работы

После успешного rollback пробрасывается исходная ошибка без замены её текстом rollback. Временная SQLite-ошибка может запустить новую попытку всей транзакции. Программная ошибка не классифицируется как временная и покидает pipeline после одной попытки.

### Ошибка `COMMIT`

Результат транзакции считается неподтверждённым. Фасад сначала пытается выполнить rollback. Повтор всей транзакции разрешён только если rollback завершился успешно и исходная ошибка commit классифицирована как временная. Такое правило предотвращает продолжение работы с открытой транзакцией.

### Ошибка `ROLLBACK`

Исход соединения и транзакции неизвестен, поэтому повтор запрещён независимо от текста исходной ошибки. Фасад выбрасывает отдельную невременную ошибку с зарезервированным префиксом верхнего уровня `litros_db_rollback_failed`, содержащую подробные представления исходной ошибки и ошибки rollback, и помечает экземпляр неработоспособным. `КлассификаторОшибокSQLite` до обхода цепочки причин проверяет, начинается ли описание верхней ошибки с точного префикса `litros_db_rollback_failed`, и сразу возвращает `Ложь`. Только при отсутствии префикса он ищет `busy`/`locked`. Поэтому диагностическое упоминание исходной блокировки не может случайно включить retry.

Фасад выполняет best-effort `Закрыть()` исходного менеджера; ошибка закрытия добавляется в диагностику, но не заменяет сведения о двух основных ошибках. Все следующие вызовы этого экземпляра фасада завершаются программной ошибкой с тем же префиксом `litros_db_rollback_failed` и требованием пересоздать контекст Autumn или перезапустить приложение.

### Программные ошибки

Нетранзакционные программные ошибки проходят через executor, но не повторяются существующим классификатором. В транзакции программная ошибка callback сначала приводит к rollback, затем пробрасывается без повторной попытки. Использование деактивированной единицы работы и попытка передать не `Действие` являются программными ошибками.

### Идемпотентность

Фасад повторяет только ошибки, признанные текущим классификатором временными ошибками SQLite (`busy`/`locked`). Он не даёт общей гарантии exactly-once для произвольного `Сохранить`. Многошаговые проверки и записи, для которых важна атомарность, должны выполняться через `ВыполнитьВТранзакции`; callback не должен выполнять HTTP, файловые или иные внешние побочные эффекты.

## Запрет вложенного pipeline и обходов

Внутри транзакционного callback все обращения к SQLite выполняются только через переданную `ЕдиницуРаботыБД`. Запрещено:

- вызывать фасад из callback, в том числе через другой уже мигрированный репозиторий;
- запускать `ИсполнительОперацийБД` вручную;
- начинать или завершать транзакцию вручную;
- получать исходный менеджер, коннектор или `ХранилищеСущностей`;
- использовать Active Record для сохранения и удаления.

Фасад не вводит глобальный флаг «транзакция выполняется», потому что такой флаг не отличит рекурсивный вызов от законного конкурентного вызова из другого потока и вместо ожидания слота ошибочно отклонит его. Вложенность предотвращается ограниченным API единицы работы, запретом внедрения внутреннего менеджера в потребителей и тестами зависимостей. Нарушение этого контракта является программной ошибкой мигрированного кода.

## Autumn DI и жизненный цикл

Текущая завязь `МенеджерСущностей` переименовывается в `ВнутреннийМенеджерСущностей`. Она остаётся единственной фабрикой исходного менеджера: создаёт строку соединения, регистрирует модели и инициализирует SQLite.

`УстойчивыйМенеджерСущностей` регистрируется как обычный singleton-желудь Autumn. `ИсполнительОперацийБД` внедряется непосредственно, а `ВнутреннийМенеджерСущностей` — обязательно через `&Табакерка`. Фасад вызывает `Достать()` только при первом DB-вызове и сохраняет полученный экземпляр; создание фасада само по себе не создаёт файл и не открывает SQLite. Так сохраняется текущая ленивая инициализация БД.

Внутренний менеджер не получает прозвищ и не внедряется ни в один мигрированный repository/service. Потребители внедряют `УстойчивыйМенеджерСущностей`; их собственная `&Табакерка` для фасада допустима, но уже не требуется для отложенного открытия базы.

Один контекст Autumn содержит один фасад, один executor и один исходный менеджер. Закрытием соединения по-прежнему владеет контекст приложения. Исключение — аварийное закрытие фасадом после неудачного rollback, после которого этот контекст считается непригодным для работы с БД.

В тестах обе зависимости фасада можно передавать напрямую или переопределять через Autumn. Отдельное имя внутренней завязи исключает случайное внедрение сырого менеджера вместо фасада.

## План миграции потребителей

### 1. `ХранилищеЗависимыхРепозиториев`

Первым мигрирует самый сложный транзакционный сценарий. Ручные `НачатьТранзакцию`, `ЗафиксироватьТранзакцию` и `ОтменитьТранзакцию` заменяются одним `ВыполнитьВТранзакции`. Все служебные методы транзакции принимают `ЕдиницаРаботыБД` и используют только её.

Вызовы `ХранилищеРепозиториев` из callback нельзя оставлять в прежнем виде: после миграции этого репозитория они создали бы вложенный pipeline. Нужные чтения и сохранения выполняются через единицу работы либо через служебный алгоритм, которому единица работы передана явно. HTTP и другая внешняя работа в callback не добавляются.

### 2. Сырой SQL в `ХранилищеРепозиториев`

Получение коннектора для `ПолучитьРепозиторииДляОбновления` заменяется на `УстойчивыйМенеджерСущностей.ВыполнитьЗапрос`. После этого repository больше не знает о коннекторе.

### 3. Простые CRUD-операции

Остальные вызовы `Получить`, `ПолучитьОдно`, `Сохранить` и `Удалить` в репозиториях переводятся на фасад. После каждого шага статический поиск подтверждает отсутствие внедрения `ВнутреннийМенеджерСущностей`, получения коннектора, хранилища и Active Record в мигрированных классах.

### 4. `ПроцессорОчередиПакетов`

Очередь мигрирует последней. Её прямую зависимость от `ИсполнительОперацийБД` и ручные вызовы `ВыполнитьОперацию` удаляют, иначе возникнет двойной pipeline. Простые чтение и удаление идут через фасад. Составная операция «проверить наличие → сохранить» выполняется через `ВыполнитьВТранзакции`, чтобы повтор охватывал проверку и запись целиком. Обновление GitHub и логирование остаются за пределами DB-транзакции.

После завершения миграции `ИсполнительОперацийБД` внедряется для операций приложения только в фасад. Сам executor и его отдельные тесты остаются доступными как инфраструктурный компонент.

## Тестирование

### Модульные тесты с `moskito`

`moskito` используется для моков исходного менеджера и executor, проверки аргументов, количества и порядка вызовов:

- каждый из пяти простых методов запускает executor ровно один раз и делегирует исходному менеджеру ровно один раз на попытку;
- возвращаемые значения `Получить`, `ПолучитьОдно` и `ВыполнитьЗапрос` не преобразуются;
- транзакция соблюдает порядок `BEGIN → callback → COMMIT`;
- при ошибке callback или commit порядок содержит `ROLLBACK` до выхода ошибки в executor;
- новая попытка получает новую активную единицу работы и повторяет всю транзакцию;
- программная ошибка не повторяется;
- ошибка rollback запрещает повтор, закрывает менеджер best-effort и блокирует последующие вызовы фасада;
- классификатор отдаёт приоритет верхнеуровневому префиксу `litros_db_rollback_failed` над вложенными маркерами `busy`/`locked`;
- создание фасада не разрешает табакерку внутреннего менеджера; первый DB-вызов разрешает её ровно один раз;
- единица работы делегирует CRUD и SQL напрямую, не вызывает executor и отклоняет вызовы после деактивации;
- параметры callback раскрываются по описанным правилам.

Ручные stateful-fixture допустимы только для поведения, которое неудобно выразить последовательностью ответов `moskito`, например для контроля состояния между двумя попытками.

### Интеграционные тесты с реальным SQLite

Для каждого теста создаётся отдельный временный файл БД. Проверяются:

- повтор простой операции после реальной блокировки `database is locked`;
- rollback снимает изменения неуспешной попытки до новой попытки;
- временная ошибка в середине многошаговой транзакции приводит к повтору всей транзакции без частичных данных и дублей;
- успешная попытка фиксирует все изменения;
- программная ошибка callback оставляет базу без изменений;
- сырой SQL через фасад использует то же соединение и настройки SQLite.

Интеграционные тесты не заменяются моками: они подтверждают реальные границы транзакции и поведение SQLite. Все менеджеры и коннекторы закрываются, временные файлы `db`, `-wal` и `-shm` удаляются.

### Регрессия

После каждой миграционной части запускаются точечные тесты фасада и изменённого потребителя. Перед завершением этапа запускается полный `oneunit execute`, статическая проверка изменённых `.os` и `git diff --check`.

## Совместимость

Публичные классы репозиториев и сервисов сохраняют свои текущие методы и результаты. Меняется только внутренняя DI-зависимость. Строка соединения, модели `entity`, настройки busy timeout/WAL и правила классификации ошибок остаются прежними.

Завязь с именем `МенеджерСущностей` не сохраняется как alias: такой alias позволил бы новому коду продолжать обходить фасад. Это намеренно несовместимое изменение только для внутренней композиции приложения и тестов, которые напрямую находили старую завязь. Они переходят на `ВнутреннийМенеджерСущностей` при проверке инфраструктуры или на `УстойчивыйМенеджерСущностей` при проверке прикладных операций.

## Критерии приёмки

- В Autumn существуют отдельные зависимости `ВнутреннийМенеджерСущностей` и `УстойчивыйМенеджерСущностей`; прикладные потребители используют только вторую.
- Фасад предоставляет ровно шесть утверждённых методов, а единица работы — пять прямых методов без управления транзакцией.
- Все простые операции и сырой SQL проходят через один executor-вызов.
- Транзакция занимает executor один раз, а её CRUD-вызовы не запускают executor повторно.
- После ошибки работы или commit новая попытка возможна только после успешного rollback.
- Ошибка rollback имеет приоритетный верхнеуровневый префикс `litros_db_rollback_failed`, не повторяется даже при наличии `busy`/`locked` в диагностике, содержит сведения об обеих ошибках и делает текущий фасад непригодным для дальнейших DB-вызовов.
- Создание и внедрение фасада не открывает БД; `ВнутреннийМенеджерСущностей` извлекается из `&Табакерка` ровно один раз при первом DB-вызове.
- Мигрированные потребители не получают сырой менеджер, коннектор, хранилище сущностей и не используют Active Record.
- В очереди отсутствуют ручные вызовы executor после миграции; проверка и добавление пакета повторяются как одна транзакция.
- Модульные тесты используют `moskito`, а реальные SQLite-тесты подтверждают блокировки, rollback и отсутствие частичных данных.
- Полный `oneunit execute`, статическая проверка и `git diff --check` завершаются успешно.
