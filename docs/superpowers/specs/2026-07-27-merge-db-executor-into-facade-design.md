# Встраивание DB executor в устойчивый фасад

## Цель

Сократить ядро отказоустойчивого доступа к БД, встроив resilience pipeline из
`ИсполнительОперацийБД` в `УстойчивыйМенеджерСущностей`, и заменить неявную
`ФиксированнаяСтруктура` именованной неизменяемой командой.

Изменение не должно менять прикладное поведение: повтор временных ошибок,
ограничение параллелизма, транзакционный протокол, fatal-state и публичный API
менеджера сохраняются.

Эта спецификация заменяет части дизайна от 2026-07-24, где
`ИсполнительОперацийБД` описан как самостоятельный компонент, а команда — как
`ФиксированнаяСтруктура` с полем `Режим`.

## Архитектура

После изменения ядро состоит из трёх компонентов состояния и одного value object:

- `УстойчивыйМенеджерСущностей` — прикладной API, resilience pipeline и создание команд;
- `КоординаторОперацийБД` — одна попытка работы с raw-менеджером, транзакционный протокол и fatal-state;
- `ТранзакционныйДоступКБД` — краткоживущий CRUD-доступ внутри транзакционного callback;
- `КомандаОперацииБД` — именованное неизменяемое описание простой или транзакционной операции.

`ИсполнительОперацийБД` удаляется. Его отдельной Autumn-регистрации и отдельной
production-зависимости больше нет.

Поток вызова:

```text
публичный метод УстойчивогоМенеджераСущностей
  -> проверка fatal-state
  -> создание КомандаОперацииБД
  -> resilience pipeline фасада
  -> КоординаторОперацийБД.Исполнить
  -> одна простая или транзакционная попытка
```

## УстойчивыйМенеджерСущностей

### Зависимости и состояние

Конструктор фасада получает обязательные зависимости:

```text
НастройкиОтказоустойчивостиБД
КлассификаторОшибокSQLite
КоординаторОперацийБД
```

Фасад хранит координатор, классификатор и созданный при инициализации
`ПайплайнОтказоустойчивости`. Значения по умолчанию и самостоятельное создание
внедряемых зависимостей не добавляются.

Существующие незакоммиченные изменения, которые уже сделали DI-параметры
обязательными, должны быть сохранены при реализации.

### Экспортный интерфейс

Прикладной интерфейс остаётся ровно из шести методов:

```text
Получить
ПолучитьОдно
Сохранить
Удалить
ВыполнитьЗапрос
ВыполнитьВТранзакции
```

Дополнительно фасад имеет один служебный экспорт:

```text
НужноПовторитьОперацию
```

Этот метод является callback стратегии повторов: он не повторяет успешную попытку
и передаёт `ДанныеОшибки()` классификатору для решения о временности ошибки.
Архитектурные проверки различают шесть прикладных методов и один разрешённый
служебный callback, а не требуют шесть экспортов всего.

### Resilience pipeline

Фасад переносит без изменения семантики текущие настройки executor:

- экспоненциальную задержку и jitter;
- максимальную задержку;
- число повторов;
- условие повтора через `НужноПовторитьОперацию`;
- ограничение параллелизма до одной операции;
- лимит очереди;
- максимальное ожидание executor-слота.

Каждый прикладной вызов сначала выполняет
`КоординаторОперацийБД.ПроверитьРаботоспособность()`, затем создаёт команду и
передаёт её pipeline вместе с действием `КоординаторОперацийБД.Исполнить`.

Для `ВыполнитьВТранзакции` fatal-проверка по-прежнему предшествует проверке типа
callback, чтобы сохранённая fatal-диагностика доминировала над контрактной ошибкой.

## КомандаОперацииБД

### Конструктор

Единый класс создаётся так:

```bsl
Новый КомандаОперацииБД(
    ИмяОперации,
    Параметры,
    ОбработчикТранзакции = Неопределено)
```

Разрешённые имена:

```text
Получить
ПолучитьОдно
Сохранить
Удалить
ВыполнитьЗапрос
ВыполнитьВТранзакции
```

Инварианты проверяются в конструкторе:

- неизвестное имя отклоняется;
- для `ВыполнитьВТранзакции` обязателен обработчик типа `Действие`;
- для простой операции обработчик должен быть `Неопределено`.

### Интерфейс чтения

Класс не экспортирует изменяемых переменных и предоставляет только методы:

```text
ИмяОперации()
Параметры()
ОбработчикТранзакции()
ЭтоТранзакция()
```

Неизменяемость является неглубокой: ссылки на переданные сущности, массивы и
произвольные параметры не копируются и не замораживаются. Неизменяема оболочка
команды и привязка её полей.

Класс не выполняет операции и не зависит от raw-менеджера, coordinator или
resilience. Это только типизированный value object.

## КоординаторОперацийБД

`Исполнить` принимает только `КомандаОперацииБД`. Получение полей структуры и
ветвление по строковому `Режим` удаляются.

Алгоритм:

```text
получить raw-менеджер с повторной проверкой fatal-state
если Команда.ЭтоТранзакция()
    выполнить транзакцию с Команда.ОбработчикТранзакции() и Команда.Параметры()
иначе
    выполнить простую операцию Команда.ИмяОперации() с Команда.Параметры()
```

Текущий протокол `BEGIN -> callback -> COMMIT/ROLLBACK`, деактивация
`ТранзакционныйДоступКБД`, сохранение исходной `ИнформацияОбОшибке`, обработка
неудачного rollback и fatal-state не меняются.

## Удаление ИсполнительОперацийБД

Удаляются production-класс и его DI-зависимость. Тесты executor не удаляются без
замены: проверки pipeline переносятся в отдельный набор отказоустойчивости фасада,
чтобы основной контрактный набор фасада не стал чрезмерно большим.

Из активных исходников и тестов удаляются:

- тип `ИсполнительОперацийБД`;
- поле и constructor dependency `_ИсполнительОперацийБД`;
- создание executor в fixtures и consumer-тестах;
- архитектурные ожидания отдельного executor-компонента.

## Совместимость и существующие изменения

Публичные шесть методов `УстойчивыйМенеджерСущностей` и поведение repositories не
меняются. Конструктор фасада является внутренней DI-композицией и меняется с двух
зависимостей на три.

Незакоммиченные изменения в `packagedef`, `КлиентGitHubAPI`, обязательных DI-параметрах
фасада и `ХранилищеОчередиПакетов` принадлежат существующему рабочему дереву.
Правка обязательного DI в `ИсполнительОперацийБД` исчезнет вместе с удаляемым файлом,
но её намерение сохраняется: настройки и классификатор становятся обязательными
параметрами фасада. Несвязанные файлы не включаются в task-коммиты.

## Тестирование

Работа выполняется через RED-GREEN-REFACTOR.

Обязательные проверки:

- контракт `КомандаОперацииБД`, включая все невалидные комбинации;
- отсутствие изменяемых экспортных полей команды;
- фасад создаёт команды правильного типа и содержания;
- фасад выполняет retry только для временных ошибок;
- сохранены задержки, jitter и ограничение параллелизма;
- whole-transaction retry создаёт новую транзакционную попытку;
- queued race и fatal dominance остаются зелёными;
- coordinator принимает именованную команду и больше не читает `Режим` структуры;
- `ИсполнительОперацийБД` отсутствует в active source/tests;
- архитектурный guard допускает шесть прикладных и один служебный экспорт фасада;
- SQLite integration остаётся зелёной;
- полный последовательный OneUnit завершается без ошибок.

Изменённые OneScript-файлы проверяются `oscript -check`; известные ограничения
global-module context фиксируются отдельно, а не скрываются.

## Критерии готовности

- `ИсполнительОперацийБД` удалён и не имеет активных ссылок.
- Фасад самостоятельно владеет единственным DB resilience pipeline.
- Команды передаются как `КомандаОперацииБД`, а не структура или набор неявных полей.
- Команда не может находиться в невалидном сочетании имени и обработчика.
- Координатор сохраняет единоличное владение raw-менеджером, транзакцией и fatal-state.
- Публичное поведение repositories/services не изменилось.
- Архитектурные, unit-, integration- и полные тесты зелёные.
