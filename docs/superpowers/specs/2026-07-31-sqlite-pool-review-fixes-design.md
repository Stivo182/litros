# Исправления ревью SQLite-пулов

## Контекст

Изменения `d6c233a^..87e70b0` заменили единый устойчивый менеджер двумя пулами SQLite-менеджеров. Ревью выявило четыре дефекта: transient-жизненный цикл пула в Autumn, общий изменяемый cache пакета `entity` между слотами одной роли, ожидание таймаута при полной потере ёмкости и невозможность ожидающего `Закрыть()` подхватить закрытие после таймаута владельца.

Код установленного пакета `entity` изменять нельзя. Исправления выполняются внутри `litros` и сохраняют публичный прикладной интерфейс `ПулМенеджеровСущностей`.

## Цели

- создать один пул на контекст Autumn;
- обеспечить отдельный `ПулСущностей` пакета `entity` для каждого SQLite-слота;
- немедленно отклонять операцию, если у требуемой роли не осталось исправных слотов;
- позволить конкурентному вызову `Закрыть()` продолжить закрытие после отказа предыдущего владельца;
- добавить регрессионные тесты для каждого дефекта;
- удалить персональный GitHub-токен из локальной конфигурации, сохранив остальные пользовательские настройки.

## Не входит в решение

- изменение исходников или опубликованной версии `entity`;
- восстановление и динамическое пересоздание сломанных слотов;
- изменение формул размеров пулов;
- изменение retry-политики SQLite;
- рефакторинг прикладных хранилищ вне необходимой адаптации тестов.

## Жизненный цикл Autumn

Завязь `ПулМенеджеровСущностей` получает характер `Одиночка` либо использует эквивалентный характер по умолчанию. Все три прикладных хранилища получают один экземпляр пула, поэтому `КоличествоЧитателей`, `КоличествоПисателей`, статистика и закрытие относятся ко всему контексту приложения.

Регрессионный тест дважды разрешает желудь `ПулМенеджеровСущностей` в одном контексте и проверяет идентичность экземпляра. Созданный пул обязательно закрывается в очистке теста.

## Изоляция состояния `entity`

Пакет `entity` ключует глобальное `ХранилищеСущностей` по типу сущности, типу коннектора и исходной строке соединения. Поэтому менеджеры с одинаковыми строками соединения разделяют один изменяемый `ПулСущностей`, даже если их SQLite-коннекторы различаются.

Каждый рабочий менеджер получает уникальный идентификатор слота. Writer и reader открывают один файл через абсолютный SQLite URI, но URI заканчивается уникальным фрагментом вида `#litros-writer-1` или `#litros-reader-1`. По формату SQLite фрагмент URI игнорируется движком, а `entity` видит разные исходные строки соединения и создаёт независимые хранилища. Writer использует `mode=rw`, потому что файл уже создан bootstrap-менеджером; reader сохраняет `mode=ro`.

При построении URI абсолютный путь экранирует символы `?` и `#`, заменяет обратные слеши прямыми и формирует Windows-путь с ведущим `/`. Это соответствует [официальным правилам SQLite URI](https://sqlite.org/uri.html) и не смешивает символы имени файла с query string или фрагментом слота.

Bootstrap-менеджер остаётся отдельным и не участвует в рабочих слотах. Он создаёт схему и устанавливает режим журнала до открытия рабочих соединений.

Интеграционные тесты проверяют одновременно два свойства:

1. менеджеры одной роли получают разные объекты `ПулСущностей`;
2. оба менеджера читают и изменяют одну физическую SQLite-базу в соответствии со своей ролью.

Тест параллельной ORM-работы использует методы `Получить` или `Сохранить`, а не прямой вызов коннектора, чтобы задействовать cache `entity`.

## Потеря ёмкости роли

Выбор слота под общей блокировкой возвращает один из трёх результатов:

- свободный исправный слот — операция начинается;
- исправные слоты существуют, но заняты — операция ожидает до `МаксимальноеОжиданиеСлотаМс`;
- исправных слотов нет либо массив роли пуст — немедленно вызывается ошибка `Пул чтения не имеет исправных слотов` или `Пул записи не имеет исправных слотов`.

Последний случай не регистрируется как ожидание насыщенного пула, потому что освобождение текущих операций не может восстановить ёмкость. Ошибка по-прежнему учитывается в общей статистике ошибок вызова.

## Передача права на закрытие

`Закрыть()` использует общий deadline одного вызова и цикл получения права на закрытие:

1. попытаться получить право;
2. если другой вызов закрывает пул, ждать изменения состояния без удержания блокировки;
3. если пул закрыт, завершиться идемпотентно;
4. если состояние остаётся `Закрывается`, но `_ЗакрытиеВыполняется` сброшено после таймаута или ошибки владельца, повторно попытаться получить право;
5. при достижении собственного deadline вернуть ошибку таймаута.

Таким образом, после освобождения права второй вызов продолжает закрытие и закрывает менеджеры, если активных аренд уже нет. Одновременно только один вызов остаётся владельцем закрытия.

## Конфигурация и секрет

Значение `litros.github.Токен` в незакоммиченном `autumn-properties.json` заменяется пустой строкой. Уровни логирования и прочие локальные изменения файла сохраняются. Отзыв уже выданного токена выполняется владельцем учётной записи вне репозитория.

## Проверка

Каждый дефект исправляется отдельным циклом RED → GREEN:

- singleton-разрешение Autumn;
- разные ORM-cache для двух слотов одной роли;
- немедленная ошибка при нулевой исправной ёмкости;
- передача права конкурентному `Закрыть()`.

После фокусных тестов выполняются:

```powershell
oneunit execute --mode summary --timeout 30000
oscript -check 'src/db/Классы/ПулМенеджеровСущностей.os'
oscript -check 'src/db/Классы/ЗавязьПулМенеджеровСущностей.os'
git diff --check
```

Фактическое имя файла с Autumn-завязью определяется по текущему рабочему дереву: пользователь уже переносит код из `ОбъектыВзаимодействияСБД.os` в `ЗавязьПулМенеджеровСущностей.os`, и реализация должна сохранить этот незакоммиченный перенос.
