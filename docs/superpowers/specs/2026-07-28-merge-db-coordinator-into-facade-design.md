# Встраивание координатора БД в устойчивый фасад

## Цель

Сделать `УстойчивыйМенеджерСущностей` единственной точкой владения отказоустойчивым доступом к БД и удалить внутренние прослойки `КоординаторОперацийБД` и `КомандаОперацииБД`.

Прикладной API фасада и поведение retry, транзакций и фатального состояния не меняются.

## Текущее затруднение

`КоординаторОперацийБД` не имеет production-потребителей, кроме `УстойчивыйМенеджерСущностей`. Он хранит сырой менеджер сущностей, фатальное состояние и транзакционный автомат, то есть внутреннее состояние самого фасада.

`КомандаОперацииБД` существует только для передачи имени операции и параметров из фасада в координатор. После объединения эта маршрутизация становится лишней. Сохранение универсального строкового диспетчера без класса команды оставило бы неявный контракт и позиционные параметры.

## Выбранное решение

Полностью встроить координатор в `УстойчивыйМенеджерСущностей`. Для каждого вида операции pipeline получает отдельное типизированное по сигнатуре действие фасада. Универсального диспетчера и строковых имён команд не будет.

Отклонённые варианты:

- один универсальный метод с именем операции — меньше методов, но сохраняет строковую маршрутизацию и неясные параметры;
- отдельный внутренний исполнитель без Autumn — меняет форму зависимости, но не устраняет лишнюю границу владения.

## Структура фасада

`УстойчивыйМенеджерСущностей` хранит:

- настройки pipeline;
- классификатор временных ошибок SQLite;
- обязательную ленивую табакерку `ВнутреннийМенеджерСущностей`;
- единожды разрешённый сырой менеджер сущностей;
- фатальную диагностику после неудачного rollback;
- блокировку состояния;
- resilience pipeline.

Конструктор напрямую получает:

- `НастройкиОтказоустойчивостиБД`;
- `КлассификаторОшибокSQLite`;
- `&Табакерка &Пластилин("ВнутреннийМенеджерСущностей")` без значения по умолчанию.

Прикладные методы остаются прежними:

- `Получить`;
- `ПолучитьОдно`;
- `Сохранить`;
- `Удалить`;
- `ВыполнитьЗапрос`;
- `ВыполнитьВТранзакции`.

Служебный интерфейс для действий pipeline содержит:

- `ПолучитьБезПовтора`;
- `ПолучитьОдноБезПовтора`;
- `СохранитьБезПовтора`;
- `УдалитьБезПовтора`;
- `ВыполнитьЗапросБезПовтора`;
- `ВыполнитьТранзакционнуюПопытку`;
- `НужноПовторитьОперацию`.

Эти методы экспортируются только потому, что вызываются объектом `Действие`. Они образуют служебный, а не прикладной контракт. Прикладные потребители используют исключительно шесть методов фасада, перечисленных выше.

Файл разделяется на области публичного API, служебных действий pipeline, управления менеджером и фатальным состоянием, транзакционного автомата и создания pipeline.

## Поток простой операции

1. Публичный метод проверяет фатальное состояние.
2. Публичный метод запускает pipeline с конкретным действием `ЭтотОбъект` и параметрами соответствующей сигнатуры.
3. Retry охватывает одну полную попытку конкретной операции.
4. Bulkhead получает слот отдельно для каждой попытки и освобождает его на время задержки retry.
5. Метод `БезПовтора` повторно проверяет состояние при ленивом получении менеджера и выполняет ровно один вызов `entity`.

Предварительная проверка быстро отклоняет новые операции после фатального сбоя. Проверка внутри получения менеджера закрывает гонку между предварительной проверкой и получением pipeline-слота.

## Поток транзакции

1. `ВыполнитьВТранзакции` сначала проверяет фатальное состояние, затем тип callback.
2. Pipeline запускает `ВыполнитьТранзакционнуюПопытку`, передавая callback и его пользовательские параметры отдельными аргументами.
3. Попытка выполняет `BEGIN`.
4. Создаётся новый `ТранзакционныйДоступКБД`.
5. Callback получает доступ первым аргументом, после него раскрываются пользовательские параметры.
6. После успешного callback выполняется `COMMIT`.
7. Доступ деактивируется, результат callback возвращается вызывающему коду.

Ошибка `BEGIN` пробрасывается без rollback. Ошибка callback или `COMMIT` приводит к rollback. После успешного rollback исходная ошибка пробрасывается в retry, и вся транзакция может быть выполнена заново.

Если rollback не удался, фасад:

- деактивирует транзакционный доступ;
- пытается закрыть сырой менеджер;
- формирует диагностику с маркером `litros_db_rollback_failed:`;
- атомарно фиксирует фатальное состояние;
- запрещает retry и все последующие обращения к БД.

Это поведение переносится без смысловых изменений.

## Изменения файлов

Production:

- изменить `src/db/Классы/УстойчивыйМенеджерСущностей.os`;
- удалить `src/db/Классы/КоординаторОперацийБД.os`;
- удалить `src/db/Классы/КомандаОперацииБД.os`;
- удалить обе записи из `src/db/lib.config`;
- не изменять repositories и другие прикладные потребители.

Tests:

- удалить `tests/КомандаОперацииБД_test.os`;
- перенести актуальные проверки координатора в `tests/УстойчивыйМенеджерСущностей_test.os`;
- заменить создание координатора прямой передачей тестовой табакерки фасаду;
- обновить fixtures, создающие фасад вручную;
- обновить архитектурный guard под пять DB-классов и отсутствие удалённых типов;
- сохранить реальные SQLite-тесты и тесты порядка retry/bulkhead.

## Проверки

Тесты должны закреплять:

- ленивое получение raw manager ровно один раз;
- отдельный pipeline-action для каждой операции и отсутствие строкового диспетчера;
- порядок `BEGIN,CALLBACK,COMMIT`;
- отсутствие rollback после ошибки `BEGIN`;
- rollback после ошибки callback и `COMMIT`;
- retry всей транзакции после успешного rollback;
- новый `ТранзакционныйДоступКБД` для каждой попытки;
- деактивацию доступа после завершения попытки;
- фатальное состояние и закрытие менеджера после неудачного rollback;
- отклонение уже ожидающей операции до обращения к raw manager;
- освобождение bulkhead-слота между retry;
- работу Autumn-композиции и реального SQLite.

Перед завершением выполняются точечные наборы фасада, классификатора и SQLite, полный `oneunit execute` и `git diff --check`.

## Вне области изменений

- изменение прикладного CRUD/SQL API;
- изменение количества повторов и порядка стратегий pipeline;
- ограничение произвольного SQL только чтением;
- рефакторинг GitHub resilience pipeline;
- объединение `ТранзакционныйДоступКБД` с фасадом.

Эти вопросы могут быть рассмотрены отдельно и не должны смешиваться со структурным объединением классов.
